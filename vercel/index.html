Windows Server Management Essentials for IIS and SQL Server

A Windows server running IIS and SQL Server has more moving parts than its CPU and memory graphs suggest. This guide covers what to check, how often, and where problems tend to start.

IIS serves the web application, SQL Server holds its data, and Windows itself sits underneath both. A fault in any layer looks the same to users, which is why Windows server management works best as a routine and not as a reaction to outages.

The routine below is one a small team can follow, or hand to server management services when in-house capacity is short.

The Three Layers to Look After

Three layers share the same server, and each one fails in its own way.

Windows Server

Operating system updates, services, disk space, event logs and the accounts that can log in.

IIS

Sites, application pools, bindings and certificates, request logs and the HTTP errors users actually see.

SQL Server

Databases, backups, SQL Server Agent jobs, memory settings, indexes and the storage underneath them.

When a page loads slowly, the cause can sit in any of the three. Checking them separately, in the same order every time, is what makes problems quick to isolate.

Patching Windows Server Without Surprises

Windows updates are the most routine task and the most disruptive when skipped or rushed. Deliver them through a controlled channel such as WSUS, Group Policy or your patch management tool, and do not leave each server to update itself at random.

Install on a test or staging server first, take a snapshot or backup before production changes, and schedule reboots inside a maintenance window. SQL Server cumulative updates and service packs are tracked separately from Windows updates, so they need their own place on the calendar. After each round, confirm that IIS sites respond and that SQL Server Agent jobs are still running.

Keeping IIS Healthy

  • Application poolsGive each important site its own pool so one failing application does not take down the rest. Review the identity each pool runs under and set recycling to suit the app.
  • Rapid-Fail ProtectionIf a pool crashes repeatedly in a short period, IIS stops it and visitors see 503 errors. Check the pool state and the Windows event log before simply restarting it.
  • LogsIIS request logs grow steadily and can fill the system drive. Archive or delete old ones on a schedule.
  • CertificatesTrack TLS certificate expiry dates so an expired certificate does not take the site down.

Keeping SQL Server Healthy

  • BackupsRun full, differential and transaction log backups to match your recovery needs, keep copies off the server, and restore them to a test server regularly. A backup you have never restored is an assumption.
  • Recovery model and log growthDatabases in the full recovery model need regular log backups, or the transaction log keeps growing until the disk is full.
  • MemorySet a maximum server memory value so SQL Server leaves enough RAM for Windows and IIS.
  • Integrity and maintenanceRun DBCC CHECKDB on a schedule and keep index and statistics maintenance in place.
  • Agent jobsAlert on failed SQL Server Agent jobs, because backups and maintenance usually run through them.

Monitoring What Matters

Pick a small set of counters and compare them with your own baseline instead of generic thresholds. Good starting points in Performance Monitor are listed below.

  • Processor(_Total)\% Processor TimeSustained CPU pressure across the server.
  • Memory\Available MBytesHow much memory is left for new work.
  • PhysicalDisk\Avg. Disk sec/Read and Avg. Disk sec/WriteStorage latency, which often explains slow databases.
  • SQLServer:Buffer Manager\Page life expectancyHow long data stays in memory. Sudden drops can signal memory pressure.
  • SQLServer:SQL Statistics\Batch Requests/secThe overall database workload.
  • Web Service(_Total)\Current ConnectionsHow many connections IIS is serving.

Feed these into whichever monitoring tool you use, such as the Windows exporter with Prometheus, the Zabbix agent, or NSClient++ with Nagios, and alert on trends as well as hard limits.

Security Basics for Windows Servers

Do not expose RDP on port 3389 directly to the internet. Put it behind a VPN or remote desktop gateway, restrict the source addresses, keep Network Level Authentication on and use multi-factor authentication where possible.

Keep Microsoft Defender or your endpoint protection current, give every administrator a named account, and use Windows authentication for SQL Server where you can. If the sa account is enabled, give it a long unique password or disable it.

Keeping the Routine Going

A routine only works if someone owns it. Assign each check to a named person, write the steps down, and review what slipped every quarter.

Conclusion

Windows Server with IIS and SQL Server stays reliable when each layer gets regular attention: patched on a schedule, backed up and restored in tests, monitored against a baseline and kept off the open internet. The routine does not need to be elaborate, but it does need to be followed.

Frequently Asked Questions

How often should Windows Server be patched?

Most teams patch monthly in a maintenance window after testing, and move faster for critical vulnerabilities. SQL Server updates follow their own schedule alongside the Windows updates.

Should SQL Server and IIS run on the same server?

Small workloads often do, but separating them isolates resource contention and limits the damage if one is compromised. Larger or busier applications generally benefit from separate servers.

Why does my IIS site return 503 errors?

Common causes are an application pool stopped by Rapid-Fail Protection after repeated crashes, resource exhaustion, or a failing back end such as the database. Check the pool state and the Windows event log first.

Is it safe to leave RDP open to the internet?

No. Put RDP behind a VPN or remote desktop gateway, restrict source addresses, keep Network Level Authentication on and use multi-factor authentication.
